# 07 · Technical Decision Record

Each decision includes the compared options, the selection, and — per the brief's explicit requirement — the WHY.

| # | Decision | Option A | Option B | Selected | Reason |
|---|---|---|---|---|---|
| 1 | Animation engine | GSAP + ScrollTrigger | Motion (formerly Framer Motion) | **GSAP + ScrollTrigger** | GSAP is 100% free since v3.13 (Apr 2025) including ScrollTrigger/SplitText, removing the old licensing objection. Motion's scroll tooling (`useScroll`/`useTransform`) is meaningfully weaker for pin+scrub+nested-gated-timeline patterns, which this build structurally requires (Advantage card-stack, horizontal gallery). Mixing both engines would add bundle weight without benefit — see research doc §3.3. |
| 2 | Smooth scroll | Lenis | GSAP ScrollSmoother | **Lenis** | Both are free now. Lenis is framework-agnostic and doesn't require the `#smooth-wrapper`/`#smooth-content` DOM restructuring ScrollSmoother mandates, which is friendlier to a Next.js App Router layout tree and to incremental section-by-section rollout. Lenis is also the de-facto standard pairing with ScrollTrigger in current production sites of this exact visual genre (research doc §3.4). ScrollSmoother remains a legitimate choice if a team is already 100% GSAP-standardized and wants one fewer dependency — noted here as the valid alternative, not a wrong one. |
| 3 | Hero centerpiece visual | Pre-rendered looping video (WebM/MP4) | Live Three.js/React-Three-Fiber scene | **Pre-rendered video** | Nothing in the 21s reference capture shows real-time interactivity (no cursor-parallax, no drag-to-orbit) on the hero object — its only motion is a slow, ambient, non-interactive shape morph. A pre-rendered loop reproduces the observed visual fidelity exactly, at a fraction of the engineering time, bundle size, and mobile GPU/battery cost of a hand-rolled WebGL scene, and trivially satisfies `prefers-reduced-motion` (swap to poster frame). Escalate to R3F only if a future requirement adds genuine input-reactivity, which is out of scope here (research doc §2.4, §3.1). |
| 4 | Canvas vs DOM | DOM (CSS/HTML + video element) | `<canvas>`-based rendering | **DOM** | Every effect identified is transform/opacity/filter/video-driven; canvas would only be justified for custom per-pixel rendering (particle systems, shader effects), none of which were observed. DOM keeps content SEO-crawlable and accessible by default, which a canvas-only render would sacrifice. |
| 5 | Framework | Next.js (App Router) | Vite + React (SPA) | **Next.js** | SSR/SSG is a hard PRD requirement (FR-001, SEO §11) for a marketing site whose content must be crawlable and fast on first paint; Vite+SPA would require bolting on a separate SSR solution to match, with no offsetting benefit for this use case. Next.js 16 is current stable LTS as of this writing (2026-09-18). |
| 6 | Scroll-orchestration primitive | GSAP ScrollTrigger | Native CSS `animation-timeline: scroll()/view()` | **GSAP ScrollTrigger** | Native CSS scroll-driven animations are not yet universal baseline — Firefox still ships the feature behind a flag as of Firefox 152 (June 2026), while Chrome/Edge (since 2023) and Safari (since Safari 26, Sept 2025) do support it. Beyond the browser-support gap, native CSS has no primitive for "pin + cover-stack + gated nested counter" or "vertical-scroll-distance mapped to horizontal translateX with a measured, dynamic end point" — both structurally required here. Native CSS scroll animations are retained as an optional, non-critical progressive enhancement only (research doc §3.5). |
| 7 | Horizontal gallery mechanism | Vertical-scroll-driven `transform: translateX` (pinned) | Native `overflow-x` horizontal scroll | **Both — segmented by breakpoint** | Desktop/laptop (and tablet down to a confirmed cutoff, TDD §11): pinned transform-driven scrub, matching the reference's exact observed mechanism (research doc §2.8 — no native scrollbar, no drag gesture observed, confirms transform-based). Mobile/touch-primary: native `overflow-x` + `scroll-snap`, because hijacking vertical scroll for horizontal motion is a well-established mobile UX anti-pattern regardless of what the desktop reference does — this is a deliberate, justified deviation from literal 1:1 reference-matching in service of the PRD's broader usability requirements. |

## Additional decisions not explicitly requested but made during research

| # | Decision | Selected | Reason |
|---|---|---|---|
| 8 | Styling approach | Tailwind CSS (utility-first) over hand-written CSS modules or CSS-in-JS | Fastest, most consistent path to enforcing the Motion Design System's token scale (spacing/radius/color) across many components without style drift; avoids CSS-in-JS runtime cost, which matters for a performance-budget-constrained page. |
| 9 | Counter implementation | GSAP tween on a plain-object value + manual `textContent` write | React state per counter tick | Writing to React state 60 times/second per active counter would cause needless re-renders; GSAP's `onUpdate` writing directly to a ref'd DOM node's `textContent` is the standard, cheap pattern (TDD §4, Animation Spec MOT-HERO-007). |
| 10 | CMS | Headless CMS or typed content collection (Sanity/Contentful/MDX) | Not a hardcoded CMS choice | Left as a client-preference decision in PRD §13 — the requirement is only that Advantage/Case content be data-driven, not which specific headless CMS product is used; this is deliberately not over-specified since it doesn't affect the motion architecture. |
| 11 | Global state management | None (local component state only) | Redux/Zustand/Jotai | No cross-route/cross-component shared client state exists in this spec's scope; adding a state library speculatively would be over-engineering per the brief's explicit "don't over-engineer" instruction (TDD §14). |
